# FunSearch population calculation check

This is a building-block check, not a public benchmark or complete reproduction. `core.funsearch_population.FunSearchPopulation` is not yet wired into the public Framework. The upstream reference is the original [programs database at `cc53f274237d7ab05c19df939edbc1f9616a7c19`](https://github.com/google-deepmind/funsearch/blob/cc53f274237d7ab05c19df939edbc1f9616a7c19/implementation/programs_database.py); the checker accepts only the exact SHA-256 recorded in `summary.json`.

Run after downloading that pinned file to a local path and providing NumPy and SciPy:

```bash
PYTHONPATH=m0 python research/experiments/2026-11-05-funsearch-population/compare_reference.py /path/to/programs_database.py
PYTHONPATH=m0 python -m pytest -q m0/tests/test_funsearch_population.py
```

The 200 seeded synthetic cases compare test signatures, the last-case score reduction, temperature-scheduled cluster probabilities, and length-based probabilities. Scores are provided in frozen sorted case order; upstream instead reduces the last key of the supplied mapping. Its RNG and exact draws differ from this component's independently seeded Python generator. The component records resets rather than discarding history, requires an island epoch for post-initial registrations to reject late writes, and permits global seeding only at initialization. When the runtime supplies an eligibility set, automatic island selection and sampling are conditioned on non-pruned candidates and remove empty clusters; this is an explicit budget-governance adaptation. The planning population stores source digests and lengths, not program text; the separate prompt builder needs selected source artifacts. The caller must serialize access; this standalone object does not provide concurrent locking or authenticate its checkpoint. Upstream uses wall-clock reset scheduling and explicitly leaves stale asynchronous writes unresolved. This comparison does not validate prompt construction, model calls, reset distribution, evaluator integration, or benchmark performance.

`check_binpacking_prompt.py` additionally checks prompt construction using the seed program in the pinned [public bin-packing notebook](https://github.com/google-deepmind/funsearch/blob/cc53f274237d7ab05c19df939edbc1f9616a7c19/bin_packing/bin_packing.ipynb); it checks the notebook hash before use. Run it with `PYTHONPATH=m0 python research/experiments/2026-11-05-funsearch-population/check_binpacking_prompt.py /path/to/bin_packing.ipynb`. This checks only prompt formation with a repeated seed, not program execution or performance.
# Reference bin-packing baseline

`check_binpacking_baseline.py` reads the pinned upstream notebook after checking
its SHA-256, extracts only literal dataset assignments (it does not execute the
notebook), and independently evaluates best-fit packing. The saved
`binpacking-baseline.json` reproduces the notebook's average bin counts: 212.0
on 20 OR3 instances and 2067.0 on five Weibull 5k instances; the respective
average L1 lower bounds are 201.2 and 1987.8. These numbers are reference
best-fit baselines, not results generated by this framework or a model.

Reproduce with `python check_binpacking_baseline.py PATH_TO_PINNED_NOTEBOOK`.
The notebook is from [DeepMind's FunSearch repository at the pinned commit](https://github.com/google-deepmind/funsearch/tree/cc53f274237d7ab05c19df939edbc1f9616a7c19);
its header attributes the software to DeepMind under Apache 2.0 and other
materials under CC-BY 4.0. The OR3 instances originate from OR-Library as
credited in the notebook. The notebook is not copied into this repository.

`PYTHONPATH=m0 python research/experiments/2026-11-05-funsearch-population/prepare_or3.py
PATH_TO_PINNED_NOTEBOOK NEW_OUTPUT_DIRECTORY` prepares a deterministic 10/10
split by sorted OR3 instance ID. It refuses an existing output directory and
records the notebook and split content hashes. The two output directories are
data preparation only: the future evaluator must mount only the development
directory during search, freeze the selected candidate, and separately mount
the held-out directory for final evaluation. This command does not establish a
sandbox or perform a model run.

The separate `core.tasks.funsearch_binpacking.score_instance` function scores
one case as the negative number of bins used, and rejects priority outputs with
the wrong shape or non-finite/non-numeric values. The built-in best-fit
priority was checked on all 20 pinned OR3 instances and matches the upstream
average of 212.0 bins. This function is for trusted callbacks: an untrusted
callback in the scorer's process could modify the scorer even inside a sandbox.
Model-generated candidates require a separate isolated execution process and a
trusted scoring boundary, with only the chosen split exposed, before model work.

An experimental `SandboxedPriority` prototype keeps the scorer in the parent
and sends only the current item and eligible-bin capacities to a separate
Bubblewrap/seccomp child. Its offline tests cover host-file and environment
isolation, invalid output and a deadline; a trusted reference function scored
the ten OR3 dev instances at -213.9, matching the split baseline. The child
does not receive the dataset or scorer module. This is not yet connected to the
Framework's durable evaluator or independently audited recovery protocol, and
the underlying sandbox is not a complete resource policy or a hostile-kernel
boundary. Do not treat this prototype as a model benchmark result.

`OR3DevDomain` is an experimental public-Framework adapter for this isolated
priority process. It binds the development file digest, ten case IDs, metric,
and function template before provider calls; it supports only unseeded dev
evaluation and exposes per-case development scores. A local fixture using the
ten pinned OR3 dev cases and a fixed best-fit function exercised construction,
scoring and recorded replay at -213.9, without any external model request.
It does not supply final held-out grading, durable child-process adoption, or
real-model results; interruption may leave a running evaluator thread until
its bounded deadline. Those are required before a reproduction claim.
