## B-1 预算错配：隐性科目吞噬主科目，记账边界画在模块边界而非成本成因上

**机制解剖**：M3 最基本的职责是回答"预算花在了哪里"。失效模式：科目体系按**模块名**（生成/评估/档案）而非**成本成因**（产生新候选 vs 维护既有候选的可信度）划分，于是某模块内部的服务性开销被记账在该模块名下，而它对主科目（产生净改进的 rollout）的吞噬在账本上不可见。GEPA（arXiv:2507.19457）是最锋利的一手案例：其 Pareto 验证表维护要求对每个候选在累积实例子集上反复重估，总 rollout 6,438 / 678 / 6,858 / 2,157（四个任务）对比纯训练 rollout 737 / 79 / 558 / 269——**约 85–90% 的 rollout 预算花在"维护验证表"这个隐性科目上**，而这笔开销在系统账目里被记作"评估"，不被记作"搜索的代价"。预算错配的机制结构：(a) 隐性科目无独立配额与独立报警，其膨胀无上限；(b) 隐性科目的收益（更准的 Pareto 前沿）与主科目的收益（更好的解）共用同一个产出指标，归因被掩盖；(c) 当总预算收紧时，隐性科目是固定成本（表必须维护），被挤压的永远是主科目——**固定开销占比随总预算下降而上升，小预算 run 的科目结构与大预算 run 系统性不同**【推断：这是跨预算尺度结果不可比的预算层成因】。

**真实案例**：(1) GEPA 四任务 rollout 分布（2507.19457，Table 2/附录）：6,438 vs 737（HotpotQA）、678 vs 79、6,858 vs 558、2,157 vs 269——验证/训练比 8.7–8.9×；作者自承须"动态选择验证子集"作为 future work，即承认该隐性科目无成本控制【原文明确】；(2) AIDE² 外环 ~90% 拒绝率（weco.ai 2026-07）：90% 的生成预算产出的候选被准入拒绝，"被拒候选的生成+评估"是一个从未出现在任何框架科目表里的沉没科目；(3) ShinkaEvolve 消融（2509.19349）：bandit ensemble 相对固定 ensemble 只 "slightly improves"——自适应模型路由这个组件本身消耗的决策/记账开销与其增量不成比例【推断成分中等：原文未单列 bandit 的记账成本】。

**为什么难防**：科目体系在系统设计的第 0 天被随手划定（按代码模块划账是零思考默认），此后所有报表在同一边界内自洽——**错配不违反任何内部一致性，只在与成本成因对齐的替代科目表对照时才暴露**，而替代科目表不存在；隐性科目的受益者（策略模块、档案模块）不承担其成本，跨模块补贴无对账；且"验证表维护是必要的"在每一步都局部正确，85–90% 是复利式累积结果（与 S 系根因 2 同根：单步合理、跨期成灾）。

**候选公理**：
- **公理 B-B1（科目按成本成因划分，隐性科目一等化）**：M3 科目体系必须区分"产生新候选"与"维护既有候选可信度"（重评/验证表/去重）两类成因；后者为显式科目、有独立配额与占比报警线（GEPA 的 8.7× 为举证锚点），占比超限须触发归因报告而非静默记账。
- **公理 B-B2（跨模块补贴须对账）**：凡模块 A 的决策在模块 B 名下产生成本（策略决定重评 → 成本记在评估），M3 须在台账中双记（B 记账、A 记消耗）；无对账能力的跨模块成本转移视为预算错配的待定证据。

## B-2 成本隐形：嵌套算子/子调用成本不上报，固定开销游离于账本之外

**机制解剖**：M2-O16（算子嵌套度）允许算子内部是完整的子搜索/agent run（SWE-Agent 式嵌套算子），接口上对上层透明（o:2^𝒮→𝒮 不变）。预算层的失效是这种透明性的镜像：**接口不变性使嵌套对内对外都不可计**——上层把一次嵌套算子调用记为"一次调用"，其内部展开的几十次 LLM 调用、子评估、沙箱时间要么不记账、要么记在内层而永不上卷。m2_axes_final 的耦合注记已点名："×O19（嵌套算子的成本必须进漏斗核算，否则预算失控）"——即设计者已知默认配置下预算必失控。三类隐形子科目：(a) **嵌套调用**——agentic 算子的内部 rollout 数是无界的（while not solved），一次"算子调用"的成本方差可达数量级；(b) **重试类开销**——Simple Baselines 的 debug-until-runs（M2 既有卡片）把失败转成延迟成本，重试消耗在报表上消失（O 系已记其"可见失败变不可见"，本文记其"成本科目消失"）；(c) **固定开销**——框架启动、档案加载、checkpoint 写盘、谱系更新、embedding 构建等每 run 固定成本，在小预算 run 中占比巨大却从不进入 per-candidate 成本核算。

**真实案例**：(1) M2-O16 耦合注记（m2_axes_final.md O16×O19）："嵌套算子的成本必须进漏斗核算，否则预算失控"——失效被预言而非被测量【既有卡片口径】；(2) aider 排行榜（2024-09 至 2025-01）：o1-preview diff 合规率 84.2%、Qwen2.5-Coder-32B 仅 71.6%——**15–28% 的编辑调用需要重试**，retry 成本使名义 token 预算与实际 token 消耗系统性偏离，而该偏离率因（模型×格式×供应商）三元组而异，无法全局折算；(3) AIDE² debug 成本结构（weco.ai 2026-07）：bug rate>15% 才挂 debug 组件是 AIDE₈₅ 进化出的策略——反证默认配置下 debug/重试开销无预算约束地附着在主流程上；(4) promptolution 评测（m2/groupC_frontier）：1M token、<$0.15 预算约束下的 prompt 优化——能给出 $ 预算上限的前提是每次调用成本已知，嵌套/重试结构恰恰破坏此前提。

**为什么难防**：嵌套透明性是架构特性而非 bug——"算子接口不变"正是模块化设计的目标，成本穿透要求每个嵌套层主动上报，上报义务随嵌套深度指数级被遗忘；固定开销在 benchmark 论文里被刻意排除（"我们报告搜索成本，不含框架开销"），排除惯例随文献扩散；且成本隐形不产生任何运行时症状——账本平衡、报表正常，只是"名义预算 100"与"实际可分配预算 70"之间有个无人认领的差额。

**候选公理**：
- **公理 B-B3（成本穿透：嵌套深度不计费豁免禁止）**：任何嵌套算子/子调用必须沿调用链上卷实际消耗（token/时间/沙箱），M3 的 per-candidate 成本记录须含"嵌套展开树"；无上卷能力的算子调用在记账时按成本上界计（先扣押金后结算）而非按名义一次调用计。
- **公理 B-B4（固定开销显式化与摊销）**：每 run 的固定开销（启动/加载/落盘/谱系）为独立科目并摊销进 per-candidate 成本；报告"有效预算率 = 进入搜索的预算 / 名义预算"为一等健康指标，小预算 run 的低有效预算率须在结论可比性声明中标注。

## B-3 节流失效：硬上限截断制造偏差数据，超额触发级联失败

**机制解剖**：配额节流的两种对称失效：(a) **硬截断偏差**——token/时间/调用数硬上限使跑到一半的 run 被终止，其产出数据是**非随机缺失**的：被截断的 run 系统性地是"探索更激进/任务更难/候选更大"的 run，若台账把截断 run 与正常完成 run 混记为同分布样本，一切基于完成数据的统计（策略增量、算子产率）被截断偏差污染；若直接丢弃截断 run，则其已消耗预算从账目与方法论双重消失（钱花掉了、数据没了、教训没留下）；(b) **超额级联**——硬上限触顶后，下游模块按"预算正常耗尽"语义处理：档案模块照常驱逐（F-B 系驱逐压力不因截暂停）、谱系照常记录代际（截断代与完整代混排）、恢复机制从快照复活时重新消耗配额——**一次超额事件沿模块边界级联成多次不可逆操作**，而 M3 没有"超限模式"语义可广播。FunSearch 的 4h 固定岛重置（Nature 2024）是配额式截断的制度化先例：固定周期砍岛在演化后期恰好截断正在突破的谱系——时间配额与搜索相位脱节时，节流机制本身就是选择压力（错误的那个方向）。

**真实案例**：(1) FunSearch 4h 固定重置（Nature 2024）被 PDE-SHARP 等生态原样继承（arXiv:2511.00183，islands=4/reset=3600s）——**失效的节流超参通过复现生态扩散**，与 S-3 记录同源，本文记其"配额周期与相位解耦"的预算层归因；(2) RelayEvolve（arXiv:2608.05651）：Fixed-switch 对照臂全败于阶段自适应切换——固定时刻表式的资源切换（配额何时转向）开环失效【既有卡片口径】；(3) aider 重试率 15–28%（B-2 已引）意味着任何"按调用数"计的配额在实际 token 维度上系统性超支——**配额计量单位（调用数 vs token vs 美元）与被控资源的错配使硬上限在错误维度上收紧**【推断】；(4) promptolution 的 <$0.15 硬预算（m2/groupC）：预算约束下的优化器对比以"同额美元"为公平前提，但不同优化器的 token 单价消耗结构不同（CAPO 93.7 vs 78.1），同额美元 ≠ 同额搜索深度——硬上限的公平性语义本身是错的。

**为什么难防**：硬上限是工程上唯一零争议的节流实现（"到数就停"写进配置即合规，与 S 系"可审计默认值偏好"同根）；截断偏差的受害者（被截断 run）不产生后续数据可自证——与 E7/S-4 的"被截断分支无后续"完全同构；超额级联发生在模块边界上，每个下游模块的单步行为都局部合理（档案按规则驱逐何错之有），失效是协议层缺失（无"超限模式"广播）而非任何单模块的错。

**候选公理**：
- **公理 B-B5（截断 run 是一等数据，不得混记或丢弃）**：被节流终止的 run/代/候选必须带截断归因标记（触顶的配额维度、已消耗量、进行到的相位）入台账；统计层消费完成数据时须声明截断处理方式（删失/加权/独立报告），混记视为数据污染。
- **公理 B-B6（超限模式广播与级联冻结）**：配额触顶 80%（软阈）即向 intent_queue 与各模块广播"收敛模式"，驱逐/重置/快照复活等不可逆操作的配额消耗须单独审批；硬触顶后进入只读结算态，禁止任何模块在超额状态下执行不可逆操作。
- **公理 B-B7（配额计量单位对齐被控资源）**：配额声明必须指明计量维度（调用数/token/美元/墙钟）及其与搜索进度（有效候选数）的换算率；换算率随（模型×供应商）漂移时，硬上限须在漂移维度上重标定。

## B-4 计费口径漂移：供应商价格/tokenizer/模型版本变更使跨 run 成本不可比

**机制解剖**：M3 的台账若同时承担"跨 run 可比性"职能（A/B 对照、预算效率趋势、退化基线重跑），则计费口径的任何漂移都使历史账目失效：(a) **价格漂移**——供应商调价（LLM API 价格在 2024–2026 年多次数量级下调）使"去年 $100 的搜索"与"今年 $100 的搜索"对应完全不同的 token 量与搜索深度；(b) **tokenizer/计数漂移**——同一文本在不同模型/同一模型不同版本下的 token 计数不同，按 token 记的账在换模型后失去共同尺度；(c) **供应商行为漂移**——aider 排行榜的一手数字：同一模型 DeepSeek-V3 换供应商（经 Novita）diff 合规率 98.7%→84.0%，**供应商变更同时改变了单位成本与单位有效产出，两个维度一起动，成本效率归因被混淆**。这与 M8 Receipt 失效同构（评估口径换版使历史分数不可比）：**M3 的"美元/token"与 M8 的"分数"一样，都是有时效、有版本的测量值，不是物理常数**【推断：两组失效共享"台账值缺版本戳"这一根因】。结构性后果：任何基于"等预算"的对照实验（SB 式同预算对照、S-B15 的退化基线）在跨期重跑时，预算等价性本身已漂移——对照的公平性前提静默失效。

**真实案例**：(1) aider 供应商切换：98.7%→84.0% 合规率（aider.chat 排行榜 2024-09 至 2025-01 多期）——同模型跨供应商的成本-质量联合漂移的一手测量；(2) promptolution 生态惯例（m2/groupC）：以 1M token、<$0.15 为预算单位对比优化器——token 与美元混用作预算单位的实例，且该惯例的可比性依赖"tokenizer 与价格不漂"这一未声明假设【推断】；(3) RelayEvolve（2608.05651）"便宜模型捕获早期大部分进展"的成本论证、Morph propose/apply 两级拆分的 1.5–2× token 效率（m2/groupC）——一切成本效率结论都以当期计费口径为前提，无版本戳则不可复现【推断：这是成本类结论的可复现性危机，与 M8 同根】；(4) M2-O3 台账教训（m2_deepdive_part1）："失败率是（模型，格式，供应商）联合分布的样本，换供应商=触发台账重置"——O 系已为一类台账建立版本纪律，M3 的成本台账尚无同款纪律。

**为什么难防**：漂移源在系统边界之外（供应商定价、tokenizer 版本），M3 无法阻止漂移只能感知漂移，而感知需要主动对账（定期重测单位成本），对账本身花预算；历史账目重写（按新口径折算旧账）在政治上不受欢迎（去年的效率结论可能被推翻）；且"记账"被普遍误解为"记数字"，版本戳/口径声明在现有框架（FunSearch/AlphaEvolve/OpenEvolve/ShinkaEvolve 的公开实现）中均无对应字段【推断：按已知代码库结构判断】。

**候选公理**：
- **公理 B-B8（台账值必带口径版本戳）**：每条成本记录须附（供应商， 模型版本， tokenizer/计数器版本， 单价表版本， 日期）；无版本戳的历史账目在跨 run 比较中降权或禁用——与 M8 Receipt 的版本纪律同构对齐。
- **公理 B-B9（跨期对照以资源量为锚，美元/token 为换算）**：A/B 对照与退化基线重跑的"等预算"以不可漂量（有效 LLM 调用数×上下文长度，或标准币 = 固定基准模型的等价 token）定义；美元/token 记账须保留到标准币的换算函数，换算函数本身版本化。

## B-5 预算与评估噪声共谋：低预算抬高噪声底，策略层全部失效从预算侧被预定

**机制解剖**：SB（arXiv:2602.16805）的 P(ShinkaEvolve > IID Random Search)=0.49 在 S 系被记录为"策略层在噪声底下的增量趋零"；其预算层投影是：**噪声底不是外生给定，而是预算分配的函数**——评估预算（每候选 seeds 数 × 验证集大小）决定噪声底高度，噪声底高度决定策略/选择/自适应全部机制的有效性强弱（EoH 在精确评估域 2,000 次查询 0.66% gap vs 纯采样 10,000 次 2.44% gap，arXiv:2401.02051——同一策略在高信噪比下增量巨大）。于是存在一个系统性共谋：总预算收紧 → M3 若按"均匀压缩各科目"或"保生成压评估"节流 → seeds 数下降 → 噪声底抬高 → S-1~S-8 全部策略失效、E6 裁决失能 → 但生成侧照常产出的"改进"实为王冠噪声。**M3 的一个节流决策可以在不动任何策略代码的情况下使整个系统的结论可信度崩塌，且崩塌在分数曲线上不可见**（分数照常波动、best 照常微涨）。更隐蔽的是方向不对称：把预算从评估挪向生成在当期报表上总是"更高效"（更多候选、更多代），其代价（结论不可证）延迟到复现阶段才暴露。

**真实案例**：(1) SB（2602.16805）：小验证集设置下复杂系统与 IID-RS 无差异，重评 10 次后差异仍不显著——低评估预算下策略增量为零的一手总量证据；(2) M8 噪声分解（arXiv:2512.21326）：预测噪声 > 数据噪声——**加 seeds/重采样比加数据更能移动噪声底**，即噪声底对评估预算的边际响应方向已被一手测量，M3 的最优预算结构应偏向重评（与 S-6 的"把预算从选挪到重评"结论在预算层合流）；(3) Archive-Sampling 显著优于固定采样（arXiv:2302.00463）——同额预算花在重评上的回报高于花在更精细选择上，预算科目间边际回报不等价的一手证据；(4) Grillotti & Cully 2023（GECCO）：档案精英重测显著低于记录值——低重评预算下账本里的"成绩"系统性虚高，预算紧缩直接转化为结论虚高。

**为什么难防**：噪声底是 E 系/M8 的观测量，M3 默认看不见它——预算控制器消费的是"还剩多少钱"，不消费"当前信噪比"，两个仪表盘的割裂使共谋无报警通道；评估压缩的收益（更多生成）即时可见、代价（噪声底抬高）延迟且归属他模块，激励全面倒挂（与 S 系根因 2 同构）；且"该给评估留多少"的正确值依赖任务噪声特性，无通用默认——这恰是 SB 的教训被各框架忽视的原因：承认它需要承认大量已发表结果运行在失效区。

**候选公理**：
- **公理 B-B10（噪声底预算是不可压缩的保底科目）**：M3 在任何节流方案下必须为评估/重评保留使噪声底低于"最小可裁决改进量"的保底预算（由 M8 的噪声测量定值）；总预算低于该保底时，M3 须拒绝开跑并报告"预算不足以产生可证结论"，而非静默压缩评估——SB 的 P=0.49 是这条公理的举证门槛。
- **公理 B-B11（科目间边际回报均衡化）**：预算分配须按各科目已测边际回报（生成一个新候选 vs 重评一个精英 vs 维护验证表）做均衡；Archive-Sampling 优于固定采样（2302.00463）这类一手证据出现时，预算结构须随证据再平衡而非锁定在初始配比。

## B-6 对照预算被挪用：自我证成科目在预算紧张时第一个被砍

**机制解剖**：S-B15（退化基线一等公民）与 B-B10（噪声底保底）在预算层有一个共同的结构性弱点：**对照类科目（退化基线重跑、消融臂、锚点重评、收据重放）的产出是"证明系统的其他部分是否有效"，不直接产生 best 分数**——在任何按产出分配预算的压力下，对照科目都排在最后、被砍在最前。机制与 S-8 的"退化自检缺失"同源但视角不同：S-8 记录架构上无对照通道，本文记录**即使有通道，预算紧张时它第一个饿死**。这是一种预算层的公地悲剧：每次挪用对照预算在当期都是理性的（分数曲线不动、交付提前），失效是跨期复合的——连续挪用 N 期后，系统的全部结论失去对照基础，且无人记得最后一次有效对照是何时（M8 Receipt 失效的预算侧成因）。AIDE² 案例（weco.ai 2026-07）从正面证明自我证成需要真金白银的制度保障：其外环 ~90% 拒绝率下仍维持分层反作弊层与对照消融，这是有意的预算保护决策，而非免费所得。

**真实案例**：(1) 消融稀缺的生态观察（S-8 已记）：多数代码进化论文只报 best-so-far 曲线，算子产率/对照臂是暗数据——**暗数据的预算层成因就是对照科目从未获得配额**【推断成分低：与 S-8 互为表里】；(2) ShinkaEvolve 三消融（2509.19349）作为"罕见的组件级归因正面案例"——其稀有性本身度量了生态中对照预算的匮乏；(3) OpenEvolve 策略硬编码（newworks_groupE_evol2）使退化对照工程上不可执行——对照预算甚至无处投放，挪用问题被架构问题掩盖；(4) hal-00519579 的 AOS 负结果传统（自适应难稳赢朴素）在 LLM 进化生态被系统性忽略——旧对照结论不随环境漂移重验，等于对照预算被永久冻结在零点【推断】。

**为什么难防**：挪用在每一步都有正当名目（"这期预算紧，先保主线"），且对照科目的价值只在失效发生时兑现（保险悖论：没出事时保费永远显得浪费）；对照预算的受益者是"未来复现/审计该系统的人"，与当期预算决策者利益错位；且无外部强制（审稿不查运行期预算分配），制度保障只能内生于 M3 的配额设计——这正是 M3 作为"框架公约执行者"的核心职责所在。

**候选公理**：
- **公理 B-B12（对照科目宪法化，挪用须走例外程序）**：退化基线重跑/组件消融/锚点重评的预算配额在 run 启动时与主科目同时锁定，默认不可挪用；挪用须显式例外记录（谁批的、理由、补跑计划），连续 N 期未补跑触发结论降权（所有待证声明自动标注"对照已过期"）。
- **公理 B-B13（对照配额与总预算同比例缩放而非余额分配）**：对照预算 = 总预算 × 固定比例（启动时声明），禁止"花完主线有剩再做对照"的余额模式——余额模式下对照的存在性依赖当期运气，制度上等于没有。

## B-7 分配粒度错配：M1 块级意图 vs M3 call 级记账，对账差额无人认领

**机制解剖**：M1 的输出是 intent（"这一代给岛 A 的探索方向 D 分配预算份额 w"），是块级、语义级、前瞻性的分配决策；M3 的记账发生在 LLM call 级（每次调用的 token/耗时），是细粒度、物理级、事后性的。两层之间缺少**结算层**（intent → 实际消耗 → 偏差 → 归因 → 反馈调整下一代 intent），产生系统性对账失败：(a) **消耗不可预测**——M1 的 intent 以"份额"计，实际成本以 token 计，份额到 token 的换算率因候选大小、重试率（aider：15–28%）、嵌套展开（B-2）而波动，intent 的兑现率漂移且无监控；(b) **偏差无归因**——某 intent 超支 3 倍时，超支来自"该方向候选普遍更长"（合理）还是"重试风暴"（失效信号）无法区分，M1 拿着失真的兑现反馈做下一代分配（S 系的乘性权重更新消费了含噪的成本信号，S-5 饿死被成本噪声放大）；(c) **差额无主**——intent 层账本与 call 层账本的差额（未兑现份额、超额消耗、跨 intent 串账）既不归 M1 也不归 M3，**对账差去哪了这个问题在现有框架中无答案**——FunSearch/OpenEvolve/ShinkaEvolve 的公开实现中均无 intent 级预算对账结构【推断：按已知代码库结构判断】。ShinkaEvolve 的 proposal/eval/db 三池配额（m4/groupA F12 卡片）是最接近的工程实践，但其配额仍是池级静态的，非 intent 级闭环。

**真实案例**：(1) GEPA 验证/训练 rollout 比 8.7–8.9×（2507.19457）——若存在 intent 级对账，"探索 intent 的 85–90% 实际消耗在验证表上"会在第一期对账中暴露；该数字以"事后论文统计"而非"运行期对账报警"的形式出现，即对账层缺失的直接证据【推断】；(2) aider 重试率 15–28% 使"按调用数计的 intent 份额"与"按 token 计的实际消耗"系统性脱节（B-2/B-3 已引）；(3) RelayEvolve（2608.05651）"对的问题是便宜模型何时把 population 移交强模型"——handoff 决策本质上是 intent 级预算重分配，其胜出（Fixed-switch 全败）证明 intent 层的预算调度有真实大增量，反衬无对账层的系统连这个决策的输入（各相位实际成本）都不准确【推断成分中等】。

**为什么难防**：结算层是跨模块公共品，M1（策略组）与 M3（记账组）都不拥有它——典型的边界塌陷区；intent 消耗预测本身难（成本方差大），使"先做简单点"的工程妥协永久化；且对账失败的症状分散表现为 S-5（饿死）、B-1（错配）、B-3（截断）的他模块表象，根因被反复误诊。

**候选公理**：
- **公理 B-B14（intent-消耗对账闭环常驻）**：每个 intent 到期时必须结算（承诺份额 vs 实际消耗 vs 产出差），对账报告（按 intent 的兑现率与成本方差）为 M1 下一代分配的强制输入；无结算的 intent 不得续约——份额分配的反馈信号必须来自对账而非名义配额。
- **公理 B-B15（对账差额显式归宿）**：intent 层与 call 层账本的差额必须入账到具名科目（重试损耗/嵌套展开/固定开销/未兑现份额），"差额"本身不得作为合法科目存在；差额率（|差|/总预算）为一等健康指标常驻报告。

## B-8 重试/回滚/复活的预算归属：debug 循环与快照回滚消耗无科目可归

**机制解剖**：M2-O12（debug 兜底）与 M4 的 buggy_leaf 复活通道（失败候选标记保留、可作 debug 亲本，m4/groupA F11）给系统加了多条"花预算但不产生新候选"的路径：debug 循环（失败候选 → 诊断 → 修复 → 重评，Simple Baselines 的 debug-until-runs 是实例）、快照回滚（O16 自修改安全的小步证据化+快照回滚）、谱系复活。预算层的失效是**归属规则缺失**：(a) debug 消耗的预算记在谁头上——记原候选（其成本无界膨胀，成本-产出比失真）、记算子（惩罚了失败率高的算子，可能恰是最有探索价值的）、还是记系统（预算蒸发）？三种归属对应三种错误的下游激励【推断】；(b) 回滚消耗——O16 的自修改快照回滚意味着"系统花预算撤销自己花预算做的事"，回滚链长度无配额、无报警，自修改 agent 可以把预算消耗在改坏-回滚循环里（AIDE² 自建反作弊层又被自己改坏的 E2 案例，其预算侧投影即此）；(c) 复活歧视/偏爱——若 debug 复活候选与新候选在同一科目竞争，按历史成本加权的任何规则都歧视复活者（沉没成本已高）或偏爱复活者（已投入成本被错误计入其"价值"，沉没成本谬误制度化）。

**真实案例**：(1) AIDE²（weco.ai 2026-07）：AIDE₈₅ 自主进化出"bug rate>15% 才挂 debug 组件、debug 读 raw tail"——**debug 预算的启用阈值本身需要被进化出来**，反证默认配置（全量 debug / 无 debug）都是失效配置；且其分层反作弊层被系统自己改坏（E2 案例），改坏+修复的预算消耗无科目【既有卡片口径】；(2) Simple Baselines debug-until-runs（2602.16805/M2 既有卡片）：失败被转成延迟成本——延迟成本的规模无测量，即 debug 科目的存在性都未被承认；(3) MDPI Robotics 15(5):98：行为复活机制是 5 种防塌缩机制之一——复活通道在生产系统中被广泛使用，但其预算归属规则在所有已知框架中缺席【推断】；(4) O16 快照回滚（m2/groupA O16）：小步证据化+快照回滚作为自修改安全默认档——每步快照的存储与回滚的计算消耗是自修改配置下的新增隐性科目，与 B-1 合流。

**为什么难防**：归属规则是会计制度问题，在"先跑起来"的框架演进路径上永远排后；debug/回滚/复活的消耗间歇性出现（失败时才发生），平稳期账本上不存在，制度设计缺乏紧迫感；三种归属方案各有正确场景，一刀切规则必然错配——**正确的归属是归因问题（这笔消耗是谁的决策引起的），而归因所需的因果链记录（intent→算子→失败→debug）恰是 B-7 对账层缺失的另一症状**。

**候选公理**：
- **公理 B-B16（修复类消耗按决策归因入账）**：debug/重试/回滚/复活的消耗必须归因到引发它的决策科目（产出失败候选的算子 intent、触发自修改的配置版本），并按归因链上卷；无归因的修复消耗记入"系统损耗"科目并常驻报告其占比，占比超阈触发审计。
- **公理 B-B17（复活候选的历史成本隔离）**：debug 复活候选参与预算竞争时，其沉没 debug 成本不得计入其"已投资价值"（防沉没成本谬误制度化），也不得计入其后续成本-产出比的分母惩罚（防复活歧视）；回滚链长度设配额上限，超限回滚链触发对该自修改 intent 的冻结。

## 隐藏结构：共同根因归纳【推断】

1. **账本按系统结构（模块/调用）划分，而成本的真实成因按决策链分布**：B-1（科目错配）、B-2（嵌套隐形）、B-7（对账失败）、B-8（归属缺失）四条失效共享同一根因——记账的天然粒度是"哪个模块发起了哪次调用"，而预算管理的正确粒度是"哪个决策（intent/算子选择/重试策略）引起了这笔消耗"。两层之间的映射（结算/穿透/归因）是跨模块公共品，无人拥有、无人建设——**M3 的核心架构职责正是拥有这个映射层：科目体系必须是决策因果链的投影，而非代码模块图的投影**（B-B1/B-B2/B-B3/B-B14/B-B16 的共同指向）。GEPA 的 85–90% 之所以以"论文附录数字"而非"运行期报警"存在，就是因为没有这层映射。
2. **预算层的测量值（美元/token/调用数）与评估层的测量值（分数）同构地会漂移、会虚高、会被共谋消耗**：B-4（口径漂移）与 M8 Receipt 失效同构，B-5（噪声共谋）与 E6 同构，B-6（对照饿死）与 S-8 同构——**M3 的台账不是物理常数记录，而是与 M8 分数台账同等级别的"需版本化、需保底、需制度保护"的测量系统**。两组失效共享同一修复语法：版本戳（B-B8）、标准币锚定（B-B9）、保底配额（B-B10/B-B12）、比例锁定（B-B13）。框架公约若只在评估层设防而不在预算层设防，防线会被从预算侧绕过——低预算抬高噪声底（B-5）是"不动任何代码就使评估失效"的合法路径。
3. **失效方向的激励不对称在预算层达到极致：省预算的决策即时可见地"高效"，其代价延迟、跨模块、归属他者**：压缩评估（B-5）、挪用对照（B-6）、硬截断（B-3）、不建对账层（B-7）在当期报表上全部表现为效率提升；其代价（结论不可证、复现失败、截断偏差、差额蒸发）在复现阶段或跨期才暴露，且暴露时归属 M8/M1/M4 的病症。这与 S 系根因 2/E 系根因 2 完全同构，但预算层多一个独有机制：**M3 掌握着其他所有模块的资源开关，其失效不表现为自身的异常，而表现为所有他模块的系统性降级**——M3 是失效放大器而非失效点，这决定了 M3 的健康指标（有效预算率、差额率、隐性科目占比、对照配额兑现率）必须是全框架的一等公民，而非内部报表。
