# Framework development priorities from implementation and four reference repositories

Research snapshot: 2026-11-04, approximately 09:52 UTC. Mori baseline examined: `53d2ba14dcc9b1575510a08333bfa08abac5dff7`. The resident implementation plan was an untracked draft at review time. This is a read-only implementation review plus this note; it does not certify subsequent implementation, tests, benchmark outcomes, or production readiness.

## Decision for the current development window

The most valuable deliverable is a verified, opt-in governed path through the existing `Framework.evolve/inspect/replay` interface. Resident controls, account attribution, protected capacity, fresh sessions and recovery must form one working path. Adding a separate baseline runner, an account summary detached from settlements, or another benchmark adapter would not close the present C1/C3 gaps.

The existing seven-stage resident plan identifies the right boundaries. The available time does not itself justify declaring all seven complete. Ship only the stages whose public-entry integration and verification actually finish; keep a clear unsupported-capability refusal for unfinished stages. In particular, an offline native demonstration cannot certify shared monetary protection or worktree recovery. The RUBRIC separately requires benchmark evidence and governance evidence; neither source-code volume nor reference-repository feature parity replaces those requirements. [M1][M2][M3]

## Actual Mori gaps at the reviewed baseline

1. **Hierarchical accounting lacks resident attribution and obligations.** `_intent` contains candidate, direction, operation, request, depth and amounts, but no governed lane, slot or derived seven-account mapping. `_totals` and remaining quotes only include operation settlements and outstanding invocation reservations. Future control capacity therefore has no owner in this authority. This is different from the older M0 ledger having account concepts. [M4]

2. **The composed scheduler runs main cycles only.** `_run` iterates `_cycle`, optionally finishes layered evaluation, and returns composed-v6 results. There is no control slot schedule or fresh-control assembly in that path. The fact that older runtime records contain IID-RS does not establish residence in configured hierarchical runs. [M5]

3. **`inspect()` mostly returns cached results.** It reads a replay certificate, but does not independently reconstruct current control completeness or seven-account reconciliation from the authoritative journal. A newly appended inconsistency must not leave a previously cached success looking valid. [M5]

4. **Configured replay executes adapters.** `replay()` creates a clone and calls `clone.run`, with certificate mode `independent_rerun`. This is honestly labeled in source. A no-new-paid-calls evidence replay must consume recorded outcomes and have no live fallback. Reusing that existing implementation unchanged cannot satisfy the proposed governed replay contract. [M5]

5. **Registry factories currently receive a common store and live adapters.** `build` passes `BuildContext` along and replaces its provider/domain as construction proceeds. This is useful assembly machinery but requires a deliberate lane-restricted view and control factory contract. Merely deep-copying `MeteredProvider` would not isolate hidden sessions or fresh sampling semantics. [M6][M7]

6. **The external CNY authority has no future-control holdback.** `CampaignBudget._read` accepts reserve/settle only, enforces one unresolved operation, and validates an exact policy shape. `reserve` checks spent plus the current upper bound, not future control obligations. A main call can consume money promised only in a separate physical ledger. Safe extension needs a versioned additive event design and rehearsal, preserving existing policy identity and all historical charges. This review did not read or alter the live ledger. [M8]

7. **The framework still has broader open work.** The latest alignment records explicitly retain configuration-level parallel pools, HITL, event subscriptions/dashboard, network knowledge and other extensions as incomplete or deferred; RUBRIC B1–B5 retain external empirical obligations. Resident governance is the immediate coherent slice, not completion of the entire framework. [M1][M2]

## Fresh review of the intended interface

The plan's optional `governance` object and private `GovernedInvocation` are preferable to new public lifecycle methods. Preserve absent-key serialization exactly, because adding even an empty governance field changes manifest/checkpoint identity. The draft correctly calls for new governed identity and old-run refusal rather than upgrading an existing run during resume. [M3][M9]

The following details should be settled in code and tests before certification:

- **Factory preflight versus invocation preflight:** validate every configured registry name/options before calling any constructor; then validate actual adapter capability bindings before any paid work. A constructor must not make paid calls. A pure schema validator cannot establish that a factory returns fresh state or supports the declared sampling parameters. [M3][M6]
- **Per-call bound versus multi-call operation bound:** a valid provider request bound does not bound an arbitrary hook that issues several requests. Protect the full operation envelope, or subtract ordinal-level usage/reservations before each request. Earlier usage remains chargeable when a later request is refused. This matters for planning, custom operators and crossover as well as control draft. [M3][M7][M10]
- **Classify from authoritative operation and lineage:** a caller should not choose a favorable account. A parentless proposal maps to explore even if it occurs after cycle zero; a failed exploit remains exploit. Restored/rehashed records must be checked against these semantics, not merely against their hashes. [M3][M4]
- **No transient free capacity at conversion:** canceling a holdback and then separately reserving the call creates an admission race. Conversion must be one ledger transition under the budget lock. External physical/currency authorities cannot honestly be presented as a distributed atomic transaction; persist preparations and block before dispatch until both agree. [M3][M4][M8]
- **Stop reasons need machine semantics:** ordinary exhaustion drains controls; user checkpoint pause does not; unknown cost, integrity fault or bound breach blocks both lanes. A generic caught exception or matching an English error string is insufficient to decide drain behavior. [M3][M5]
- **Sampling assumptions remain visible:** per-draw fresh objects, fixed prompts and frozen settings establish local isolation, not an unverifiable claim about a remote service's stochastic independence. The adapter binding should expose supported seed/sampling semantics and limitations. [M3][R1]
- **Exact request comparison:** a control score is not automatically comparable with the main incumbent after adaptive fidelity changes. Use a fixed comparable evaluation request for the comparison, or report incomparable evidence; do not use a same-named metric as proof of equivalence. [M3][M10][R1]
- **Explicitly missing evidence:** failed/unresolved/incomparable planned slots must survive reporting. Do not redraw until successful, silently reduce the denominator, or promote a completed subset into a C3 formal pass. [M3][R2]

The plan already recognizes most of these risks. The review's strongest open design requirement is the still-unspecified versioned provider binding/quote payload and currency event migration schema: implementing methods with the proposed names is not enough to freeze their semantics. Until those are specified and independently exercised, refuse formal protected paid controls rather than inferring the guarantee. [M3]

## Small usability improvement worth finishing in this window

Add one installed-artifact demonstration using the same governance schema for the supported native and worktree adapters. It should print the initial plan identity and protected capacity, run a tiny deterministic fixture, pause/resume if supported, and report `planned/completed/failed/unresolved`, each account by physical unit, the stop disposition, and replay mode. Invalid configurations should fail before calls with a specific missing capability. This directly addresses A6 and catches public wiring failures that unit tests of the ledger cannot expose. It does not require a new CLI, dashboard, event bus, or public Framework method. [M2][M3][A1]

Defer new benchmark families, arbitrary plugin catalogs, UI work, automatic retry strategies, and claims of framework completion until this vertical path is demonstrated. The reason is the present dependency chain, not that those features lack long-term value.

## Follow-up: clean v71 acceptance failure diagnosis

The parent task subsequently supplied failed clean-source acceptance `20261104T093152.150968Z-t4hewpnb`. Its worktree group had 96 passes and two failures at `WorktreeCommandExecutor._wait`: `child.wait(timeout=5)` raised after `process-result.json` had already passed terminal binding validation. The full regression command later exceeded its 600-second verifier limit. Those original records remain unchanged.

Live observation during a bounded reproduction showed a supervisor in Linux `D` state at `jbd2_log_wait_commit`; memory was ample and load was modest. The disk-backed owner-SIGKILL subset separately yielded three passes and a failure of its 15-second test helper waiting to reach final audit. This establishes substantial filesystem latency during the reproduction, but does not uniquely prove the cause of the full-suite timeout.

The precise production race is reproducible independently of machine load: `command_worker.atomic` fsyncs the result file, renames it to its visible terminal name, then fsyncs the directory. The coordinator observes that filename while the trusted supervisor is still completing its final durable flush. Its unrelated five-second child-reap timeout can therefore reject an already completed, measured evaluation. A new real-subprocess regression injected a 5.25-second delay at that final directory fsync on tmpfs and reproduced the exact original `TimeoutExpired` in 5.53 seconds.

The scoped fix changes only the post-validation supervisor reap to `child.wait()`, allowing its trusted final flush to finish. The supervisor's actual evaluator execution deadline is unchanged; no process is retried or killed, and the coordinator does not skip the flush. `m0/tests/test_composed_worktree_durable_flush.py` checks preserved score and seven tokens, one execution, final flush completion and repeat adoption without another call. It skips its Linux-specific fault injection on other systems.

Verification: the new regression plus all tests in `test_composed_worktree_executor.py` and `test_composed_worktree_framework.py` passed, **59 passed in 55.82 seconds**, with `--basetemp=/dev/shm/mori-durable-flush-green`; the original owner-SIGKILL cases are included. `git diff --check` passed. This is targeted evidence, not a new full-suite or versioned acceptance certificate. The separate disk-backed test-helper timing sensitivity and 600-second full-suite timeout remain visible limitations for the integration verifier.

An old detached supervisor, PID 407047/start ticks 3234575, belonged to the timed-out acceptance fixture `test_state_mutation_interrupti1`. It had `supervisor.json` but no `authorized.json`, target or terminal result and was sleeping for authorization. It was reported to the parent task and was not killed by this investigation. No production-paid invocation was made.
