# M7 configured construction and immutable artifacts

Status: Tasks 1–5 implemented and locally verified, including public schema-2 native integration, isolated controls, immutable Git publication and command recovery; V9 external currency support and original paid-prompt/artifact audit are integrated; whole-branch review and v74 acceptance remain Task 6. No full M7 closure is claimed. Baseline f7ab27395b7907b851196ad7a88b38dd7bf5986d. User authorized autonomous development; choices below are engineering decisions, not new user approvals. Original alignment/RUBRIC remain binding.

## Intent and current mismatch

Original unified abstraction M7 and SPEC §9 require execution role, frozen/free hypothesis and authorized context projection to affect candidate-to-artifact construction in an isolated workspace. At baseline PromptOperator produces Proposal.artifact; InProcessExecutor evaluates it and WorktreeCommandExecutor writes it into per-evaluation scratch. Passing ExecutorSpec as metadata would leave M7 unimplemented.

Introduce a real construction module, with native and Git worktree artifact adapters, then evaluate the immutable result across all splits. Do not include concurrent dispatch in this work package: M7-03 remains open and its complete scheduling/recovery/CNY requirements are not removed. Existing paid pilot and live ledgers remain unchanged.

## Approaches considered

1. Add ExecutorSpec fields to current evaluator wrappers: rejected because generation remains in M2, configuration need not affect generated bytes and repeated evaluations could rebuild.
2. New all-in-one executor with separate materialization budget phase, ContextPack v2 typed sections and new control/CNY reservation schemas: expressive, but changes three authorities/contracts despite unchanged physical candidate-production semantics.
3. Two-entry construction/evaluation module; M2 supplies declarative recipes; generation and artifact publication occur in the existing operator operation envelope: selected. Reuse the single budget/meter/ordinal authority while binding new materialization semantics through new runtime identities. This choice does not preclude a separately governed build phase later if the physical contract genuinely changes.

## Interface and ownership

Use canonical ExecutorSpec; do not create a second role/hypothesis concept. A new private composition execution module exposes:

- async materialize(plan, *, operation) -> Materialization
- async evaluate(materialization, request, *, operation) -> EvidenceRecord

ConstructionPlan holds a detached Candidate, a declarative ConstructionRecipe, a resolved ExecutorSpec, and an already retrieved ContextPack. Materialization is an immutable canonical record with final Proposal-compatible artifact, source/effective hypothesis, artifact digest/commit, spec/projection/plan hashes, measured construction cost/coverage, actual attempt history and terminal outcome reference. Exact classes, codecs and registration names are fixed in the implementation plan before coding.

The module owns validation, role rendering, projection, provider output decoding, bounded implementation repair, artifact publication, protected-path checks and recovery matching. It receives provider, artifact backend and durable store dependencies; it must not receive arbitrary runtime/frontier/memory objects. Native/domain and command/worktree evaluation retain producer-bound canonical evidence. Operation identity links to an existing reservation and never creates another authority.

M2 built-ins become declarative draft/reflective/crossover recipes in the new runtime. Prompt generation moves to a real prompt materializer. Recipes carry task, selected parent artifact references and chosen hypothesis, not another copy of raw retrieved memory or full OperatorRequest.strategy. Parent artifacts are explicit construction inputs selected under existing lineage permission; arbitrary parent feedback is not a second hidden retrieval channel. Existing artifact-producing operators remain supported by the old runtime or an explicitly labelled prebuilt compatibility adapter; prebuilt does not claim role-directed generation.

## Projection

The existing composed ContextPack v1 has query, scope, memory and grounding; it has no summary section. New composed execution uses an explicit default projection [memory, grounding], with selectable content fields memory, grounding and query. Empty selection is supported. Reject summary, unknown/duplicate names and full aliases before any provider request in this contract; preserve the legacy ExecutorSpec default only for old executor callers. This is an explicit composed vocabulary, not a silent reinterpretation.

Projection validates the candidate's context_pack_ref, retains source-pack digest, scope and complete provenance for included entries, detaches nested mutable data and hashes exact projected content. It neither retrieves nor summarizes. The materializer receives only the selected projection plus explicitly allowed task/parent artifact/recipe inputs; no unprojected strategy/context copy. ContextPack v2 typed summary can be a later separately specified M5 change if needed, not invented here to make the default string appear supported.

## Role and hypothesis

Role is a nonempty validated role name bound to a versioned generation instruction definition. Built-in general/coder/analyst roles and explicitly registered custom role definitions have behavioral tests; unknown roles fail preflight. Avoid an undocumented closed list. Role instruction and version are included in the actual generation request and persisted binding.

Resolve the initial hypothesis from the candidate plan, optionally constrained by ExecutorSpec.hypothesis. Conflicts in frozen mode fail before generation. Builder output is strict JSON containing artifact and effective hypothesis; optional feedback is data, not authority. In frozen mode every repair sees the same hypothesis and changing the declared hypothesis yields a measured failed construction with no evaluation. In free mode persist original and each updated hypothesis; the scored candidate uses the final effective hypothesis. String identity does not prove semantic adherence of arbitrary generated code; document that limit.

Repairs are bounded by max_attempts and the existing operator reservation/provider call limits. Only local implementation validation feedback may guide repair. Held-out evaluation never repairs or materializes.

For a native provider without a declared hard per-call bound, the runtime stops further repairs once measured token usage consumes the reservation. One unbounded call can overrun that reservation; the original bill remains charged. This is not a pre-dispatch hard token ceiling. Governed providers retain their existing declared hard per-call bounds and protected future capacity.

## Physical and currency accounting

Candidate production stays one existing operator operation: reserve once, start once, one provider meter with monotonically increasing ordinals across recipe and materializer, persist terminal materialization, settle once. One attempted node, zero evaluation counts. No nested reset of governance ordinal state. Paid M2 activity, if supported, is inside the same envelope; recipes for the built-in default path are pure.

Actual evaluations each keep their independent existing operation. Construction cost is not added to EvalResult.cost a second time. Known construction failures retain their actual cost and typed failed outcome. Unknown completion retains the whole construction reservation and blocks new paid calls; known provider currency receipts remain authoritative without inventing a physical aggregate bill. Existing per-call CNY protection must cover every build/repair request and future control obligations. No old ledger migration, no clearing pending state, and no real supplier calls in implementation verification.

## Artifacts and workspaces

Native adapter persists immutable content-addressed artifact bytes and is explicitly trusted in-process, without a sandbox claim. Git adapter materializes the protected base in an isolated worktree, writes the final artifact, verifies protected paths and publishes a commit before any evaluation. A single artifact path is the current scope; arbitrary multi-file agent editing is not falsely certified.

All dev, incumbent refresh, calibration, admission and final evaluations consume the same recorded artifact digest/commit. Evaluation scratch may copy/check out identical bytes; it cannot invoke generation. Existing bubblewrap/process identity/measurement protection remains for command evaluation. New recommended execution profile defaults to Git artifact isolation; prompt-native evaluation must be able to consume a Git-published artifact without requiring a command evaluator. Use an explicit managed artifact repository when no base repository was provided, never snapshot unrelated caller files. Legacy profile/default behavior must remain clearly labelled until an intentional documented default migration is verified.

## Recovery and controls

Persist the construction identity before dispatch, per-provider outcomes/ordinals through existing machinery, and a content-bound terminal materialization before settlement. Adopt a complete outcome; reconstruct deterministic publication from a certified original provider terminal result; start a provably never-started suffix once; retain unresolved active native work. No lost completion authorizes a replacement call. Publication uses a persisted commit plan so a crash after commit is adopted, not committed again.

The same materialization/evaluation methods perform recovery, rather than a second parallel orchestration protocol. Recorded replay consumes stored outcomes and never invokes provider/materializer/domain. Exact spec, role version, projection, artifact and workspace bindings are verified before reuse.

Each control slot receives a fresh executor/materializer/provider/domain session and namespace, its frozen initial task/context and parentless recipe. No main memory/frontier/artifact state is visible. Construction remains within its protected operator reservation. The global fixed execution specification is frozen into the new control plan binding; lane-specific execution overrides are not silently inferred. Controls remain outside main selection/admission.

## Builder-check resolutions

Two important questions were raised by a fresh builder review; both are resolved from the isolation requirement rather than asking the absent user.

1. **Indirect hypothesis channel.** In the v9 path, policy observation exposes task and numeric/identity frontier metadata, not raw feedback/artifact/history text. Selection keeps existing eligibility rules. After the one M5 retrieval, ideation receives the selected execution projection, not the full ContextPack; it may receive only explicitly selected parent artifacts. M2 recipe construction and dynamic instruction processing receive that same permitted view. Never give these producer paths a raw pack and then try to filter only the last prompt. Trusted third-party Python with external/global state is not sandboxed; the guarantee concerns supplied interfaces. Tests place a unique sentinel exclusively in excluded current-pack content, absent from task/config/parent artifacts, and use a policy that echoes everything it receives. The sentinel must not reach the chosen hypothesis or materializer. Do not claim information-theoretic erasure of facts already present in independently authorized task or parent artifact inputs.

2. **Feedback and instruction skills.** New reflective/crossover recipes receive selected parent artifact references and numeric public comparison metadata. Raw parent feedback/insight is available only if selected by the single scoped M5 retrieval and its projection; empty/truncated retrieval intentionally means unavailable feedback. This is documented new-runtime behavior, not a silent change to legacy operators. Static user-configured InstructionSkill text becomes an explicit versioned construction-instructions tuple bound in the plan; it remains distinct from retrieved source evidence. Other skill adapters must declare and obey the projected-input execution contract before v9 preflight accepts them. They may not receive hidden unprojected context or arbitrary full strategy dictionaries. Unknown contracts fail before paid work. Role, skill instructions and recipe identifiers are all bound to the artifact receipt.

The existing operator operation is explicitly recorded as a **candidate-production envelope** in v9 construction events: M2 recipe and M7 build/repair substages have distinct recorded identities under one physical intent and a continuous provider ordinal. The event does not claim that old operator records already had M7 semantics. Unknown whole-envelope physical use remains reserved while known per-call provider/CNY evidence stays available; reports must distinguish incomplete aggregate accounting from zero usage.

## Public native integration decisions

Schema 2 creates distinct planning and feedback-absorption instances from the same policy configuration, with separate checkpoint and component-store namespaces. Raw feedback can still be absorbed into M4 memory; planning receives it through the selected M5 projection. This closes an observed bypass where a policy retained excluded feedback in its own state across checkpoint restoration and later echoed it into a hypothesis. Custom policies that require shared implicit absorb/ideate state must transfer that information explicitly through M5. Schema 1 keeps its original behavior. Arbitrary shared Python globals or external state remain outside this interface guarantee.

The constructor factory receives no live model or evaluator dependency. The measured construction invocation supplies the provider. Generation-facing policy/operator/skill factories have scoped journal views and no direct evaluator dependency. Existing memory, frontier and knowledge authorities retain their required journal access. Built-in recipes and role registration live in a pure module separate from runtime orchestration so default registration does not create a dependency cycle.

The Task 3 baseline accepts only the native in-process evaluator. Task 4 adds the explicit git_artifact executor, retaining legacy git_worktree configuration behavior; external providers remain rejected until explicit Task 5 runtime and audit support. Completed materializations are verified against the original construction terminal and artifact bytes during resume, inspect and recorded replay. Replay consumes recorded outcomes without new provider or evaluator work.
