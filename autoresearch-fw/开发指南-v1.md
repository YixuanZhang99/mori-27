## M1 Policy —— 调度器（M0 口径）

**M0 中只保留三样：greedy parent_sample（K1 的调用方）、AllocationIntent/IntentReceipt（K2 本体）、StopActionTable 查表（K5 的消费侧）。其余全部扩展化。**

```python

class AllocationIntent:      # 字段全集见 M1-UNIFIED §4；M0 只用六个核心字段
```

### 2. 默认行为（M0）

- **每代**：greedy argmax 选父 → 组装 intent → put 进 intent_queue → 拿到 Receipt 后执行 → M9 Verdict → 查表。无 idle 槽、无 scheduled 槽。
- 【内核】greedy 供亲、固定预算 intent、查表停机。
- 【扩展：塌缩报警首现】H2 有效供亲数监控 + 强制伴随检查（T-H1 降级为扩展触发后再启用——注：这是对 v1.2 强制伴随条款的**有意放松**，理由：M0 阶段候选池极小、塌缩无从发生；风险已登记，触发条件即装回条件）。
- 【扩展：单 run 预算超阈值】相位信号、phase_switch。
- 【扩展：永不在 M0】inject、learn_govern、pressure_control。

### 3. 公理锚点（M0 内仍生效的）

### 4. 分歧锚点（改默认值前必读）

## M2 Operator —— 算子（M0 口径）

**M0 中只保留 K1（draft + reflective improve + 确定性 patcher）与 K4（四段漏斗），外加三个谱系字段（parent_ids / prompt_version / apply_attempts）。其余全部扩展化。**

### 1. 接口签名（M0 内核子集）

```python
# ---- K1：统一纯函数签名，依赖全入参 ----
def op(llm, cfg: OperatorSpec, task_desc, *input_nodes,
       feedback: FeedbackView) -> VariationProposal:
    """M0 只注册 draft(0 元) 与 improve(1 元, reflective)。
    reflective improve 输入 = 当前 prompt + 评估轨迹文本（GEPA 形态）；
    LLM 只产提案，落地与判定是确定性代码（I-LLM）。"""

@dataclass
class OperatorSpec:            # M0 最小字段集
    op_id: str
    kind: Literal["draft", "improve"]
    prompt_version: str        # ● 强制，进谱系；空=拒绝注册
    representation: str = "full_rewrite"   # GEPA 负载=prompt 全文；代码负载才用 diff_block+patcher

@dataclass
class VariationProposal:
    proposal_id: str
    parent_ids: list[str]      # ● 回放必需（RUBRIC C4）
    patch_text: str            # 原文存档
    apply_result: Literal["ok", "retry_ok", "failed"] = "failed"
    apply_attempts: int = 0    # ● 失败在重试之前计数（C4 精神，M0 保留）
    similarity_records: list = field(default_factory=list)
    # 字段位预留：M0 允许为空；新颖性闸装回时恢复"缺失=拒绝入库"

# ---- K4：四段漏斗（每代每算子一条）----
@dataclass
class FunnelRecord:
    operator: str
    generation: int
    proposed: int = 0
    applicable: int = 0
    runnable: int = 0
    admitted: int = 0          # 过 M9 门数；B1 自证的数据源
    cost: dict = field(default_factory=dict)   # 对接 K3 账本
```

完整类型（ContextRecipe / DiversityProbe / 全字段 OperatorSpec）见 M2-UNIFIED §2——M0 不落，扩展装回时引入。

### 2. 默认行为（M0）

- **每代**：M1 选定父本 → draft/improve 产提案 → 确定性落地（失败先计数再重试）→ 四段计数递增 → 评估 → M9 准入填 admitted。
- 【内核】退化基线 IID-RS 同跑（K6 共享义务，不可移除）。
- 【扩展：near_dup 上升/多样性报警】新颖性闸 + 多样性探针（预期最早触发）。
- 【扩展：失败子代率 >20%】debug 算子 + 兜底。
- 【扩展：换用 LLM-judge 评估 = 硬触发】带宽闸完整版（剥离器 + 类型层白/黑名单）。M0 有意放松 C8，仅限客观可验证评估任务。
- 【扩展：T≥ExecutorSpec】自修改四件套；【扩展：C10 三前置】bandit/RL/meta。
- 【永不进 M0】crossover/merge、op tax 精细定价、full trace 进 prompt（流向禁令永久有效）。

### 3. 公理锚点（M0 内仍生效的）

| 行为 | 公理 | 测试 |
|---|---|---|
| LLM 产提案、代码落地 | I-LLM | 单测：apply 路径无 LLM 调用 |

| ~~C8 带宽闸完整版 / C3 强制相似度~~ | 有意放松，硬触发装回 | 见 §2 |

### 4. 分歧锚点

## M8/M9 Evaluator + AdmissionGate —— 评估与准入（M0 口径）

**M0 保留：确定性 judge + per-item EvalResult（含 text_feedback / public-private 分离）+ 单规则 flip_count + ReliabilityMeta 最小集 + noise_floor_zero + Receipt/Verdict + GateEvidenceRecord。噪声底是内核不是扩展（B1 自证依赖它）。**

### 1. 接口签名（M0 内核子集）

```python
@dataclass
class ItemResult:
    item_id: str
    verdict: Literal[0, 1]          # per-item 二值，M0 强制非空数组的单元

@dataclass
class ReliabilityMeta:              # B1 自证的前提，M0 内核
    n_trials: int = 1
    ci95: Optional[tuple[float, float]] = None
    noise_floor: Optional[float] = None   # 效应量 < 噪声底 ⇒ 计零

@dataclass
class EvalResult:
    candidate_id: str
    head_sha: str                   # ● 评 A 晋升 B 在类型层不可能
    items: list[ItemResult]         # ● 强制非空
    combined_score: float           # display-only，永不进终裁
    public: dict                    # 喂变异器
    private: dict                   # 定存活
    text_feedback: str              # ● S-4：GEPA 生命线，缺失=评估失败
    reliability: ReliabilityMeta
    evaluator_version: str          # ● 换裁判可溯源（RQGM 对应字段）

@dataclass
class Verdict:                      # M0 只用 ACCEPT / REJECT
    kind: Literal["ACCEPT", "REJECT"]
    rationale_ref: Optional[str]    # 拒绝须附可证伪理由（B8 精神保留）

@dataclass
class Receipt:                      # append-only，K5 主体
    verdict: Verdict
    head_sha: str
    evaluator_version: str
    evidence_refs: list[str]        # 指向 GateEvidenceRecord

# 判定规则：M0 封闭枚举只有两条
#   flip_count       —— |F| >= |B|，消费 items[]，永不消费 combined_score
#   noise_floor_zero —— 效应量 < noise_floor ⇒ 零效应（B1 与 IID-RS 对照的裁决规则）
```

完整类型（EvaluationCard 全卡 / Scope / 多值 VerdictKind / 五条件失效）见 M8M9-UNIFIED §2——扩展装回时引入。

### 2. 默认行为（M0）

- **每代**：确定性 judge 逐 item 评分 → EvalResult（含 text_feedback）→ flip_count + noise_floor_zero 裁决 → Verdict → Receipt 落 append-only 日志 → M1 查表。
- 【内核】IID-RS 对照的显著性裁决走同一 noise_floor_zero 规则（B1 验收路径）。
- 【扩展：评估成本 >50% 预算】级联三档。
- 【扩展：换用 LLM-judge = 硬触发】isotonic 校准 + position-swap/κ 探针 + M2 带宽闸（同一触发器，两侧同时装回）。
- 【扩展：评估器/门规则首次版本变更】票据失效引擎完整版（五条件+级联作废）。
- 【扩展：agent 可修改评估环境的负载 = 硬触发】B3 只读隔离 + ≥3 异构通道（RUBRIC B3 验收前必须装回）。
- 【扩展：评估器成为瓶颈的实测证据 + 四前置】EvoEvaluator（RQGM 形态，见 §5 裁决）。
- 【永不】LLM 终裁、评估器无门共进化、combined_score 作终裁输入。

### 3. 公理锚点（M0 内仍生效的）

| 行为 | 公理 | 测试 |
|---|---|---|
| 终裁只消费 items/private/reliability/head_sha | B2/分歧2 | 静态扫描 Gate.consume 白名单 |
| combined_score 永不进终裁 | 分歧2 | 同上（黑名单） |
| 无 CI 不报数、低于噪声底计零 | B7 | 单测：噪声底内 Δ → REJECT/零效应 |
| 确定性终裁 | I-LLM/B4 | 单测：裁决路径无 LLM 调用 |
| Receipt append-only | I-谱系 | S-5：无 update/delete API |
| ~~B6 三通道 / B8 探针伴生~~ | 有意放松，硬触发装回 | 见 §2 |

### 4. 分歧锚点

| 想动什么 | 分歧号 | 翻案条件 |
|---|---|---|
| gate-not-rank（现 flip_count） | §7-分歧2 | 终裁唯一形态，无配置；要排序只能加级联粗筛扩展 |

### 5. RQGM 复审裁决记录（D3 义务，2026-10-26）

**裁决：留通道、不进内核、默认永久关闭。** RQGM 三件套 = 我方既有设计的投影（epoch 冻结≈evaluator_version 分段；锚点验证≈meta-gate 硬门；记录作废≈失效条件④），不新增设计。

### 2. 默认行为（M0）

- **run 启动**：control 科目按 5% 与主科目同时锁定（普通转账不可触及）+ reeval 保底校验（预算 < M8 噪声测量保底 → 拒绝开跑并报告"预算不足以产生可证结论"）。
- **每次 API 调用前**：硬上限拦截；触顶后只读结算态。
- 【扩展：跨供应商/跨期对照 = 硬触发】多币种+汇率表+标准币（RUBRIC B2/B4 前必装）。
- 【扩展：长 run/不可逆操作出现】软阈广播+级联冻结；【扩展：首次正式 benchmark 前】M3HealthProbe 四指标、效率双指标（B5 测量工具）。
- 【永不】M3 自动降档（分配单一作者=M1）、仅监控告警档、按模块名划账、单价指标决策用途、低于保底开跑。

### v56：Bubblewrap seccomp 危险系统调用拒绝清单 ✅

- **固定策略**：`core/executor/seccomp.py` 定义 x86_64 syscall 编号、显式危险调用集合和 classic BPF。过滤器先检查 `AUDIT_ARCH_X86_64`，架构不匹配即 kill；清单内调用返回 `EPERM`，其余调用 allow。非 x86_64 失败关闭，不从宿主头文件动态猜测策略。
- **持久化与防篡改**：ProcessJournal spec 保存规范 filter base64 和 SHA256，启动 journal 只保存不含 bytes 的公开摘要。启动前必须精确重构同一版本策略；即使攻击者修改过滤器并重算无密钥 digest，也无法通过语义校验。环境变量和凭据不进入策略或 spec。
- **统一 fd 生命周期**：`materialize_seccomp()`／`seccomp_arguments()` 创建、写入并 rewind memfd，替换唯一 `--seccomp` 占位符，通过 `pass_fds` 交给 bwrap；Popen 成功后父进程立即关闭自己的 fd。detached wrapper 与 MLE solution 的直接 Popen 共用该实现，避免只验证命令行而未真正安装过滤器。
- **覆盖路径**：真实 `ptrace(PTRACE_TRACEME)` 必须返回 `-1/EPERM`；普通 Python、ExternalCommandEvaluator、GitWorktreeExecutor 和 MLE host/governed 本地官方夹具继续成功。fork 继承相同策略且证据独立，owner-crash 只接管原 outcome，不重建过滤器或重启进程。`seccomp=False` 只显式关闭 seccomp，`sandbox=None/False` 仍是另一层显式选择。
- **实测边界**：首轮完整回归发现 MLE 直接 Popen 未替换占位符，已提取共享接口并新增直接 Popen 回归；修正后 485 项完整本地回归通过。`verifier/v56/` 重跑真实探针、资源／恢复／治理和全部当前行为，CI 更新为 v56。
- **严格边界**：这是 denylist，不是完整 allowlist、cgroup、完整资源限制或恶意内核边界；不认证非 x86_64、ExternalCommandLLM／任意 proposer 的 Bubblewrap/seccomp、机器断电、外部 benchmark、USD 效率或 A/B/C 总体达标。

### v57：ExternalCommandLLM direct-prctl seccomp ✅

- **显式 delivery**：seccomp spec 新增 `bwrap_memfd` 与 `direct_prctl` 两种机制；旧 v56 spec 未记录 delivery 时仍按 `bwrap_memfd` 解释。ProcessJournal 在创建 started 记录前校验 policy 与 delivery，durable spec 保存完整策略和机制，公开 journal 只保存无 filter bytes 的摘要。
